# treehouse

Treehouse gives a git branch its own worktree plus an isolated
docker-compose stack (unique compose project, unique host ports, cloned
dependencies) so several branches — including several agent sessions — can
run fully live at once without colliding. This skill is about *using* an
adopting repository's treehouse setup, not building treehouse itself.

## Is this repository treehouse-enabled?

Check for `.treehouse.yml` at the repository root first. If it isn't there,
this repository hasn't adopted treehouse — don't suggest `treehouse`
commands; work in the main checkout as normal, or point the user at
`docs/adoption.md` in the treehouse repository if they want to adopt it.

## Getting an isolated environment for a branch

```
treehouse create <branch> --json
```

This is idempotent per branch: running it again for a branch that already
has an instance is safe — it exits 0, reports the existing instance
(`"existing": true` in the JSON), and brings the stack up if it was
stopped. It never creates a second instance for the same branch, so it's
always safe to call at the start of a task without checking first whether
one already exists.

Always pass `--json` in an agent context and parse the single JSON document
on stdout (human-readable chatter goes to stderr, and warnings are printed
to stderr too, so they won't corrupt the JSON on stdout). The fields that
matter most:

- `path` — the instance's worktree directory. Treat this as the working
  directory for everything else you do on this branch.
- `ports` — a map of the manifest's `ports.env` variable names to the
  actual host ports allocated to this instance (e.g. `{"HTTP_PORT": 4640}`).
- `urls` — human-facing URLs with those ports already substituted in.
- `state` — where the instance landed in the provisioning state machine
  (`worktree-created`, `deps-cloned`, `stack-up`, or `provisioned`;
  `provision-failed` if a hook or reconcile step failed). Only
  `provisioned` means the stack is fully up and dependencies are current.
- `compose_project` — the docker-compose project name, useful if you need
  to run raw `docker` commands against this instance's containers.

If `state` comes back `provision-failed`, the instance is left inspectable
rather than rolled back — read the create/provision output (streamed to
stderr) for what failed, fix it, then `cd` into the instance's `path` and
run `treehouse provision --retry`.

## Running commands inside the instance

`cd` into the `path` from `create`'s JSON, then use:

- `treehouse exec <service> -- <command...>` — run a one-off command inside
  a running service's container (e.g. `treehouse exec web -- php artisan
  test`, `treehouse exec db -- psql -U app`).
- `treehouse compose <args...>` — raw `docker compose` passthrough with
  `--env-file`/`--project-name` already injected for this instance, for
  anything `exec` doesn't cover (`treehouse compose logs -f web`,
  `treehouse compose ps`).
- `treehouse up` / `down` / `restart` / `status` — context-aware compose
  wrappers; run from inside the instance so they apply to its stack, not
  the main repository's.

Do not construct your own `docker compose --project-name ...` invocations by
hand — `treehouse compose`/`exec` already resolve the right project name
and env file for wherever you're standing.

## What never to do unprompted

- **Never run `treehouse remove` (or `treehouse prune --force`) without the
  user's explicit go-ahead.** Removing an instance deletes its worktree and
  releases its port claim; `remove` additionally deletes named volumes by
  default. When a branch has been merged or abandoned and its instance
  looks like a candidate for cleanup, say so and ask — don't remove it
  yourself, even if the worktree is clean.
- `treehouse down` (stopping the stack, not removing anything) is fine to
  run on your own when you're finished with an instance for the session —
  it's the same operation the project's own Claude Code SessionEnd hook
  performs (see `claude/README.md` in the treehouse repository).
- Never hand-edit `.treehouse.env` — it's regenerated by treehouse and any
  edits are overwritten on the next `treehouse provision`.
- Don't run `git worktree remove` directly against an instance's worktree;
  go through `treehouse remove` (after confirming with the user) so the
  port claim is released too.

## Exit codes

Every treehouse command follows the same exit-code contract, useful for
deciding whether to retry, ask the user, or treat a failure as fatal:

| Code | Meaning |
|---|---|
| `0` | Success |
| `1` | Generic failure |
| `2` | Port pool exhausted |
| `3` | Dirty-tree refusal (an operation needed `--force` to discard uncommitted changes) |
| `4` | Provision failed (instance left inspectable; fix and `provision --retry`) |
| `5` | Not inside a treehouse-enabled repository (no `.treehouse.yml`) |
| `6` | Docker (or the compose plugin) unavailable |
| `7` | Would have prompted in non-interactive mode (e.g. `switch` with no TTY, or `remove`/`prune` needing confirmation without `--force`) |

A non-interactive agent session always looks like "no TTY" to treehouse, so
commands that would otherwise prompt (`remove` without a name, `prune`
without `--force`, `switch`) fail with exit `7` instead of hanging. Don't
work around this by inventing a fake TTY — surface the exit-7 case to the
user (for `remove`/`prune`) or fall back to `treehouse path <name>` /
picking the instance yourself from `treehouse list --json` (for `switch`).
